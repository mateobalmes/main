How SQL actually reads

The one idea that makes SQL click: it isn't read top to bottom. The database does FROM first, then filters, then groups, and only picks your columns near the end. That's why a column you invent in SELECT can't be used in WHERE — it doesn't exist yet when WHERE runs.

OrderClauseIn plain English
1FROM / JOINWhich table(s) am I looking at, and how do they connect
2WHEREThrow away rows I don't want
3GROUP BYCollapse the survivors into groups, usually one per customer
4HAVINGThrow away whole groups I don't want
5SELECTDecide which columns come back
6ORDER BYSort the result
7LIMITOnly give me the first N rows

The single most useful habit: when a count looks wrong, comment out everything below FROM and add conditions back one at a time. The line where the number jumps is your bug. That's 90% of audience debugging.

Query 1

Count an audience

The foundation

How many people are in this audience?

Plain English: look at the customers table, count the distinct customer IDs where marketing consent is true. Distinct matters — if a customer appears on several rows you'd otherwise count them twice.

Why this job needs it: this is the query you run when marketing says the audience looks too small. Half of "the CDP and the send tool disagree" problems are a missing DISTINCT on one side.

Query 3

Join profiles to behaviour

The workhorse

Consented customers who have actually ordered

Plain English: take the customers table, attach their orders by matching customer ID, then keep only consented customers with at least one completed order. A join is just "line these two tables up using a shared key."

SELECT DISTINCT ccAn alias — a nickname for the customers table so you can write c.email instead of customers.email..customer_id, c.email
FROM customers AS c
INNER JOININNER JOINKeeps only rows that exist in BOTH tables. A customer with no orders disappears from the result entirely. orders AS o
  ONONThe matching rule — which column in one table lines up with which in the other. Get this wrong and you get either no rows or wildly too many. c.customer_id = o.customer_id
WHERE c.marketing_consent = TRUE
  AND o.order_status = 'completed';
Returns: customer IDs and emails for consented customers with at least one completed order.
Why this job needs it: targeting almost always spans tables — profile attributes in one place, behaviour in another. This is the pattern Campaign Classic's query builder generates under the hood.
Gotcha — the big one: a join multiplies rows. A customer with 12 orders appears 12 times. That's why DISTINCT is here. If an audience count suddenly balloons, a join without DISTINCT is the first suspect.

Query 4

Exclude a suppression list

The one that matters most

Everyone except people on the suppression list

Plain English: take all consented customers, look for them on the suppression list, and keep only the ones who weren't found. The trick is joining and then keeping the non-matches.

SELECT c.customer_id, c.email
FROM customers AS c
LEFT JOINLEFT JOINKeeps every row from the left table whether or not a match exists. Where there's no match, the right table's columns come back empty (NULL). suppression_list AS s
  ON LOWERLOWER(...)Forces text to lowercase before comparing. Emails are case-insensitive in practice but databases compare them exactly, so Jay@x.com wouldn't match jay@x.com without this.(c.email) = LOWER(s.email)
WHERE s.email IS NULLIS NULLThe whole trick. After a LEFT JOIN, a NULL on the right side means "no match was found" — so this keeps exactly the people NOT on the suppression list.
  AND c.marketing_consent = TRUE;
Returns: the sendable audience — consented, not suppressed.
Why this job needs it: this is suppression logic in its simplest form, and it's the query behind the single most important rule in email: never send to someone who opted out. In production this belongs upstream in the CDP, not in each send tool — but the logic is this.
Gotcha: NOT IN looks like an easier way to do this and is a trap. If the suppression list contains a single NULL, NOT IN returns zero rows and you'll think your audience is empty. LEFT JOIN ... IS NULL or NOT EXISTS are the safe patterns.
Query 5

Count per customer

Grouping

Customers with three or more orders in 90 days

Plain English: collapse the orders table down to one row per customer, count their orders, and keep only customers whose count is three or more. GROUP BY collapses, HAVING filters the collapsed groups.

SELECT
  customer_id,
  COUNT(*) AS order_count,
  MAXMAX(...)The largest value in the group. On a date column that means the most recent one — handy for "last seen" or recency.(order_date) AS last_order
FROM orders
WHERE order_date >= CURRENT_DATE - INTERVAL '90 days'
  AND order_status = 'completed'
GROUP BYGROUP BYCollapses many rows into one per unique value. Here: one row per customer instead of one per order. Every non-aggregated column in SELECT must appear here. customer_id
HAVINGHAVINGLike WHERE, but it filters GROUPS after counting, not individual rows before. You cannot put COUNT() in a WHERE clause — this is why HAVING exists. COUNT(*) >= 3;
Returns: one row per qualifying customer, with their order count and most recent order date.
Why this job needs it: frequency-based audiences — loyal, frequent, at-risk — are all this. It's also how you sanity-check whether a segment definition is doing what the brief asked.
Gotcha: WHERE runs before grouping, HAVING after. Putting the date filter in HAVING would count all orders ever and then filter, giving you the wrong customers.

Query 7

Bucket into tiers

Segmentation

Label each customer by recency

Plain English: walk down a list of conditions and use the first one that's true, like an if/else. Turns a raw date into a label a marketer can actually use.

SELECT
  customer_id,
  CASECASESQL's if/else. Checks each WHEN in order and stops at the first true one, so the order of conditions matters.
    WHENWHEN ... THEN"If this condition is true, use this value." Conditions are tested top to bottom. last_order >= CURRENT_DATE - INTERVAL '30 days'  THEN 'active'
    WHEN last_order >= CURRENT_DATE - INTERVAL '90 days'  THEN 'cooling'
    WHEN last_order >= CURRENT_DATE - INTERVAL '365 days' THEN 'lapsed'
    ELSEELSEThe catch-all when nothing above matched. Without it, unmatched rows come back NULL — which is usually a bug, not a decision. 'dormant'
  ENDENDCloses the CASE block. Followed by AS to name the new column. AS lifecycle_stage
FROM customer_summary;
Returns: every customer with a lifecycle label — active, cooling, lapsed or dormant.
Why this job needs it: this is a lifecycle segmentation in one clause, and it's the kind of derived field that belongs defined once centrally rather than reinvented in every campaign. That's a standards argument, which is your job.
Gotcha: because CASE stops at the first match, ordering the conditions loosest-first would put everyone in one bucket. Always go tightest to loosest.
Query 8

Reconcile two counts

Debugging

Who's in the CDP audience but not in the send tool?

Plain English: take the list from system A, subtract the list from system B, and look at what's left. This is the query that answers "why did 40,000 people not get the email."

SELECT customer_id FROM cdp_audience
EXCEPTEXCEPTSet subtraction — rows in the first query that don't appear in the second. Called MINUS in some databases, including Oracle.
SELECT customer_id FROM send_tool_audience;

-- and the totals side by side--A comment. Everything after it on the line is ignored. Use comments to leave notes for whoever reads the query next, including you.
SELECT 'cdp' AS source, COUNT(DISTINCT customer_id) FROM cdp_audience
UNION ALLUNION ALLStacks two result sets into one. ALL keeps duplicates; plain UNION removes them and is slower.
SELECT 'send_tool', COUNT(DISTINCT customer_id) FROM send_tool_audience;
Returns: first, the missing IDs. Second, two rows showing each system's count side by side.
Why this job needs it: their posting asks you to "verify activation dataflows" and "debug audience counts and sync issues between CDP and activation tools." This is literally that query. It's worth saying out loud that count drift between systems is something you'd monitor, not just investigate when someone complains.
Gotcha: a gap isn't always a bug. Suppression, consent changes and identity resolution all legitimately shrink an audience between the CDP and the send tool. The useful question is whether the gap is explainable, not whether it's zero.
Query 9

Tidy it with a CTE

Readability

Name your steps instead of nesting them

Plain English: WITH lets you define a named intermediate result, then use it below like a table. Same logic as a nested subquery, far easier to read and debug. Use this whenever a query grows past about ten lines.

WITHWITHStarts a CTE — a Common Table Expression. A named temporary result you can reference below, which keeps queries readable. recent_buyers ASname AS (...)Names the block. You can chain several, separated by commas, and each one can reference the ones above it. (
  SELECT DISTINCT customer_id
  FROM orders
  WHERE order_date >= CURRENT_DATE - INTERVAL '30 days'
    AND order_status = 'completed'
),
sendable AS (
  SELECT customer_id, email
  FROM customers
  WHERE marketing_consent = TRUE
)
SELECT s.customer_id, s.email
FROM sendable AS s
INNER JOIN recent_buyers AS r ON s.customer_id = r.customer_id;
Returns: consented customers who bought in the last 30 days — same as nesting it, but you can run each block on its own to see where a number goes wrong.
Why this job needs it: targeting logic gets handed between people. A query someone else can read is a documentation decision, not a style preference — and their posting cares a lot about documentation and key-person risk.
Gotcha: CTEs don't make a query faster. They make it readable. If something is slow, the fix is filtering earlier and joining on indexed keys, not restructuring with WITH.
Query 10

Handle nulls

The silent bug

Treat missing consent as "no"

Plain English: NULL means "unknown," not "false" or "zero." Comparing anything to NULL gives NULL, not true — so rows with NULL quietly vanish from your filters. This is the most common reason two people get different audience counts.

SELECT
  customer_id,
  COALESCECOALESCE(a, b)Returns the first value that isn't NULL. A safe default — "use a, but if it's missing use b."(marketing_consent, FALSE) AS consent_safe,
  COALESCE(lifetime_orders, 0) AS orders_safe
FROM customers
WHERE email IS NOT NULLIS NOT NULLThe only correct way to test for presence. Writing "email != NULL" never matches anything, because any comparison with NULL returns NULL rather than true.
  AND COALESCE(marketing_consent, FALSE) = TRUE;
Returns: customers with an email and explicit consent, with missing values defaulted rather than silently dropped.
Why this job needs it: on consent specifically, defaulting NULL to FALSE is the compliant choice — absence of consent is not consent. That's a CASL point as much as a SQL one, and worth saying that way.
Gotcha: never write = NULL or != NULL. They always fail silently. It's IS NULL and IS NOT NULL, always.

The five that cause most wrong numbers

  1. Missing DISTINCT after a join. A customer with 12 orders counts as 12 people.
  2. NULL comparisons. = NULL never matches. Rows vanish silently.
  3. NOT IN with a NULL in the list. Returns zero rows, looks like an empty audience.
  4. Date windows across time zones. UTC versus local shifts your boundary by a day.
  5. Filter in HAVING that belonged in WHERE. Counts everything, then filters — wrong customers.

If he asks how you'd debug an audience

Say the method, not the syntax. Most candidates recite clauses; the method is what a platform PM is hired for.

  1. Count both sides independently — CDP and send tool — with DISTINCT on each.
  2. Subtract one from the other and look at actual IDs, not just the delta.
  3. Check the explainable causes first: suppression, consent, identity resolution, and the sync window.
  4. Strip the query to FROM and add conditions back one at a time. The line where the number jumps is the bug.
  5. Then decide whether the gap needs fixing or documenting — and whether it should be monitored as drift rather than investigated on complaint.
